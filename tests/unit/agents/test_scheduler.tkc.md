Tests `core.agents.scheduler` by importing it (X7.2). The file it replaces declared its own `cronmatches`/`duenow`/`nextrun` — including a hand-rolled cron matcher the product does not have — and so reported a working scheduler while saying nothing about the module. The real `checkcron` recognises exactly THREE literal cron strings by string equality (`0 * * * *`, `0 2 * * *`, `0 2 * * 0`) and never consults the clock; the module says so itself in the reason it returns. This file pins that down rather than papering over it. Covers: the three recognised patterns firing; an unrecognised pattern NOT firing and quoting itself in the reason, an empty schedule not firing, and an extra space making a recognised schedule unrecognised — the trap that follows from the matcher being string equality rather than a parser; the provisional reason string, asserted so that a real parser landing turns this file red deliberately; and `checkdue` dispatching on trigger type, with all four event-driven triggers (`manual`, `filechange`, `webhook`, `mcpevent`) refusing to auto-fire and only `$schedule` delegating to `checkcron`. The `$agentdef` fixtures are full struct literals because toke has NO assignment to a struct field (T-26) and `x.trigger=v` raises E2002 whose suggested fix is a silent no-op. **The gap is asserted directly**: the same agent checked at two timestamps 25 years apart gives the same verdict, so `currenttimeepoch` is ignored and a scheduled agent is reported due on EVERY check — anything calling `checkalldue` on a timer fires every scheduled agent every tick. Verified able to fail by inverting the manual-trigger assertion. Depends on `std.test`, `std.str`, `core.agents.scheduler`, `core.agents.types`.
