The file it replaces declared its own `$agent` struct and constructor and then asserted the defaults it had just written, which is true of the copy by construction. That matters more here than elsewhere in the suite because these defaults are a GOVERNANCE control: an agent runs on a schedule, spends money and touches files with no human present, so the gap between `enabled:false;requiresapproval:true` and the opposite is the gap between an opt-in automation and one that starts working the moment it is defined. Covers, against the real `newagent`: the four arguments carried through; and every safe default — disabled, approval required, lowest risk level, NO permissions at all, no schedule, manual trigger, a non-zero but small cost ceiling (zero would mean "no ceiling was set", which a `cost>max` check reads as block-everything and a `max>0` check reads as allow-everything), and unset ownership rather than a fabricated owner. For `newrun`: the agent id and trigger recorded, the initial state `running` rather than idle, a start stamp present, completion/outcome/error empty, and a 32-hex-character id that DIFFERS between two runs of the same agent — a collision there would make the run log unreadable and per-run cost attribution wrong.
