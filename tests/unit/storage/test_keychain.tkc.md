Tests `core.storage.keychain` by importing it (X7.2). The file it replaces declared six stand-ins — a `keychainretrieve` with hardcoded credentials, a `maskcredential` the module does not have, and a `credentialcount` returning the constant 2 — and asserted that the openai key is `"sk-test-1234"`, a value three lines above it in the same file. Kept rather than deleted, even though `tests/integration/test_keychain_e2e.tk` covers the round trip, because of one property neither covers: the ACCOUNT NAMING. `setapikey` prefixes with `api_key.`, and the e2e test "verifies" that by calling `str.concat` itself. This file asserts it through the module — `setapikey("p";k)` then `getkey("api_key.p")` — and asserts the negative, that the unprefixed provider name is not an account, so a reader that forgot the prefix finds nothing. Also covers the set/get/has/delete round trip, overwrite (a rotated key that reads back as the old one), and that an unknown or deleted account reads as empty rather than as a stale value. Every account is unique to this test and deleted at the end, because `SecItemCopyMatching` blocks on an authorisation dialog when the reading binary is not the one that stored the item — leaving items behind is how the suite hangs rather than fails. Depends on `std.test`, `std.str`, `core.storage.keychain`.
