Tests `core.storage.keychain` by importing it (X7.2). The file it replaces declared six stand-ins — a `keychainretrieve` with hardcoded credentials, a `maskcredential` the module does not have, and a `credentialcount` returning the constant 2 — and asserted that the openai key is `"sk-test-1234"`, a value three lines above it in the same file. Kept rather than deleted, even though `tests/integration/test_keychain_e2e.tk` covers the round trip, because of one property neither covers: the ACCOUNT NAMING. `setapikey` prefixes with `api_key.`, and the e2e test "verifies" that by calling `str.concat` itself. This file asserts it through the module — `setapikey("p";k)` then `getkey("api_key.p")` — and asserts the negative, that the unprefixed provider name is not an account, so a reader that forgot the prefix finds nothing. Also covers the set/get/has/delete round trip, overwrite (a rotated key that reads back as the old one), and that an unknown or deleted account reads as empty rather than as a stale value. X8.7: nothing touches the user's login keychain. The test creates a throwaway keychain file under its own throwaway HOME (`std.keychain.create`), selects it (`std.keychain.use`, which redirects every later keychain call in the process and disallows user interaction) and destroys it at the end; it stops before its first keychain call if either step fails. It also proves the redirection reaches the production module: an account `core.storage.keychain` wrote to keychain A is absent (kind `notfound`) after switching to a second throwaway keychain B and present again after switching back. Depends on `std.test`, `std.str`, `std.keychain`, `std`, `core.storage.keychain`.
