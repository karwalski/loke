Tests `core.memory.decay` by importing it (X7.2). The file it replaces declared its own decay curve — LINEAR, one point lost per day out of a thousand — while the module's curve is EXPONENTIAL, a half-life applied with `math.pow`. They are not approximations of each other (after 30 days the stub says 970/1000 and the module says half), and fourteen assertions agreed with the stub perfectly while saying nothing about the module. Covers the default retention policy in `defaultconfig`, which is the part a reviewer needs to read off a test: the 30-day half-life, a non-zero score floor below a full score, a positive sweep interval, and — the load-bearing one — that `prunebelow` is strictly BELOW `minscore`, since a prune threshold at or above the clamp makes every memory deletable the moment it reaches the floor. **Carries one deliberately failing assertion, as a marker.** `apply`'s float return is corrupted across the module boundary: measured as `2` for a memory created now (correct: 1.0) and `-inf` at ages of 30, 60 and 3650 days and at starting scores of 0.4, 0.8 and 1.0, while `$decayconfig`'s struct fields read back perfectly from the same module in the same run (30, 0.1, 0.05). That is the signature of T-20, recorded for `f64` and holding here for `f32`. It is LATENT — checked, not assumed: nothing outside `packages/core/src/memory/decay.tk` imports this module, and the only consumer, `sweeprows`, calls `apply` intra-module. **It matters because of the ordering**: `sweeprows` deletes a row when `apply`'s result is below `prunebelow`, so `-inf` would be true for every row and wipe the whole palace; today `sweep` cannot run at all because `memory_scores` does not exist, so fixing M1.7 before this is a total data-loss event. `sweep` and `refresh` are not exercised for that reason.
