Tests `core.governance.incidents` against the real `incidents` table (X7.2). The file it replaces declared its own incident array and its own severity constants — `f=sevp0():str{ <"P0" }` compared to the literal `"P0"` — and never labelled itself a stub. The real constants are what the table stores and `statusresolved()` is half of `listopen`'s WHERE clause, so a silent rename would leave resolved incidents on the open list forever. Covers: the severity ladder and status vocabulary from the module; table creation read back from `sqlite_master` rather than inferred; `openincident` returning a 32-character id, writing exactly one row, and setting status `open` itself rather than trusting the caller; the full lifecycle with the assertion that makes `listopen`'s predicate meaningful — an incident under INVESTIGATION is still open, and only `resolve` takes it off the list while retaining the row, because an incident log that deletes on resolve has no history; the resolution note, which is the only record of why something was closed; and `autoopenifdegraded` on both sides of its `< 0.5` threshold, checking the row count after each so that "returns false" and "opened nothing" are separate claims. Also asserts the auto-opened incident is P2 and names the model in its title, and that `formatincidents` carries severity and title into the operator's view. Depends on `std.test`, `std.str`, `std.file`, `std`, `std.db`, `core.storage.db`, `core.governance.incidents`. T10.2 (2026-09-24): three of the backlog row's seven behaviours have no equivalent and are reported absent rather than invented — `list_all` (`listopen` is the module's only listing), `get` by id (nothing reads a single incident) and `post_incident_template` (no template, no post-incident review anywhere in the module); `append` is not separate from `openincident`. The closest observable for the `get`-unknown case is now asserted: naming an id the table does not hold changes no row and creates none, and leaves the open list as it was. Recorded there as a measured defect, reported and not fixed, is that both `resolve` and `updatestatus` return TRUE for an unknown id — an UPDATE matching no row is not an error in SQLite and neither function checks how many rows it touched, so a caller resolving a mistyped id is told the incident is closed while it is still open. The assertion is written on the table rather than the return value so it holds before and after that is fixed. Also added: with every incident resolved the open list is EMPTY while both rows are retained and marked resolved — which is what a `list_all` would read — and an empty list still renders its header row, so "no incidents" cannot be mistaken for "the view is broken".
