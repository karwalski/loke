Tests `core.governance.scorecard` by importing it (X7.2). The file it replaces declared its own `$providerstats` with its own hardcoded numbers; importing the real module showed the stub was not a simplification of it but a COPY, hardcoded numbers and all — `buildscorecard` ignored `store`, contained no query, and returned three literal stat blocks, so a fresh installation that had never sent a request reported 89 requests to anthropic with a P99 of 3100ms. That was reported as a finding during this epic and has since been **fixed in the module** (same defect class as DA1.5): every figure is now derived from `audit_log`. This file was rewritten against the repaired module and asserts that derivation.

Covers: an empty trail yielding NO provider rows, since a row of zeroes is itself a measurement claim; the provider list coming from the trail, so only providers actually used appear and a new one appears without a code change (openai does not appear until it is used — the old module reported 34 requests for it on every installation); request counts, average latency rounded rather than truncated, and P99; cost summed in exact integer HUNDREDTHS, because `audit_log.cost_usd` is a REAL whose rendering SQLite owns — that broke the audit chain's digest twice — and because a bare f64 crossing a module boundary is corrupted (T-20); the figures changing when a row is added, which is the inverse of what the old module did; and **GA5.19**, the figure the module deliberately refuses to produce — `audit_log` has no success/failure discriminator, so `errorsrecorded` is false and the formatter prints `n/r` rather than a number, asserted along with the negative that no `0.0%` appears anywhere, because that would state no request has ever failed.

**Two things a reader needs to know before running it.**

1. It needs `build/interfaces` and the loke archive regenerated from the current source. Until then it reports COMPILE_ERROR, because the committed interface still describes the old fabricated struct. It was verified against a locally emitted interface and object for `packages/core/src/governance/scorecard.tk`.

2. **Six of its 39 assertions are RED, on a live defect with one cause** — `scorecard.tk:99` passes an aggregate to `core.storage.db.countquery`, which returns `rows.len`, the number of rows the query returned, not the value of an aggregate inside them. It is correct for its documented purpose (the existence predicate behind `tableexists`/`triggerexists`), but `SELECT COUNT(id)` returns exactly one row, so it yields **1** for any provider with at least one request. Measured on a trail of three anthropic requests: `countquery("SELECT COUNT(id) AS cnt …")` → 1, `countquery("SELECT id …")` → 3. Because `n` is reused, one line produces three wrong figures — `requests` 1 instead of 3, `avgcostperreqhundredths` 100 instead of 33, and `p99latencyms` 100 instead of 900 (the offset is computed from `n`, so n=1 gives offset 0 and the `ORDER BY … ASC` query returns the sample MINIMUM). The last is self-evidently wrong from inside the data: the reported P99 is below the reported mean. The two figures that do not go through `n` — `avglatencyms` and `totalcosthundredths` — are correct, which is what localises the cause. Left in the honest direction rather than characterised, because unlike the defects in `core.governance.forecast` and `core.governance.approval` this one has a live caller: `statsfor` runs on every card.

Note on the alias: `sc` is a RESERVED token in toke (`i=sc:…` fails with "expected import alias, got 'sc'"), hence `scard`. Depends on `std.test`, `std.str`, `std.file`, `std`, `core.storage.db`, `core.storage.audit`, `core.governance.scorecard`.
