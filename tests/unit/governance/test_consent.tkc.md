Tests `core.governance.consent` against the real `consent_records` table (X7.2). The file it replaces had no table, so none of the three ways consent can be absent was reachable — and answering those correctly is the only fail-closed property this module has. Covers all three, each of which must answer FALSE: no row at all, a row with `granted=0` (what `revoke` leaves behind, so revocation is recorded rather than erased), and a row whose expiry has passed. Also covers: consent being per purpose and per user, so a telemetry grant is not read as consent for cloud routing; re-granting after revocation leaving ONE row, since `(user_id, purpose)` is UNIQUE and the upsert is what stops the second grant being a constraint error whose arm is easy to lose; the stored expiry timestamp; and `loadprefs` with the exact purpose spellings it asks for — including the negative, that a grant recorded as `companionsync` does NOT satisfy a reader asking for `companion_sync`, because the symptom of that drift is a user who has consented to everything and a product that behaves as though they consented to nothing, with the rows in the table to contradict it. The lapsed-consent case writes `expiry_ts` directly, since `grant` only accepts a positive number of days. Depends on `std.test`, `std.str`, `std.file`, `std`, `std.db`, `core.storage.db`, `core.governance.consent`.
