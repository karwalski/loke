Tests `core.feedback.store` and `core.feedback.types` against the real `feedback` table (T12.1). The file this backlog row names has never run: it exists only under `_archived-tests/`, which `scripts/run_tests.sh` excludes from discovery, it is written against a pre-toke API (`db.newmemorystore`, `str.arraypush`, no `main()`), and two of its assertions could not have passed anyway — it saved one thumbs-down and asserted `thumbsdown > 1`. The row's strongest clause is the PRIVACY INVARIANT, and it is asserted against the SCHEMA rather than against a struct, because "this entry has no prompt in it" is trivially true of anything the test constructs: the table is pinned at exactly ten named columns, and no column name may match prompt, text, content, response, body or message. Feedback is collected on every interaction, so this is the most likely place for prompt text to arrive by accident, and adding a column for it now fails a test instead of passing a review. Also covers `save` writing one row with the rating and feature-area LABELS the readers match on (`getsummary`'s `rating='thumbs_up'`, learning's `GROUP BY feature_area`); `created_at` as a real 19-character datetime rather than the five-character SQL literal GA5.1 removed; `pendingsubmission` returning all three entries and the labels mapping back to their sum variants; `getsummary`'s counts individually rather than through the rate, since a ratio cannot distinguish 1-of-3 from 10-of-30 and the rate is what `autoopenifdegraded` opens an incident on; the window in BOTH directions, with a row dated 2020 excluded by a one-day window and included by a ten-year one; and the empty case through `buildsummary(@())`, which must be a rate of exactly 0.0 rather than 0/0. The row's two FILTERS do not exist — the module's only selective read is `submitted=0` — so what is asserted is that the stored labels are selective enough for a filter to be built on, and `clear` has no equivalent at all: nothing in the module deletes a row. Two measured defects are recorded as comments and reported rather than fixed: `marksubmitted` marks ONLY THE FIRST id it is given, because its loop body begins with `<` (a return) at store.tk:163, so three ids in leaves two entries queued; and a free-form `$other` area gains a second "Other: " prefix on every round trip, because buildpendingentries (store.tk:111) rebuilds `$other` from the whole stored label and `arealabel` (types.tk:84) prefixes it again. The assertions around both are written on the row rather than the return value, so they hold before and after either is fixed.
