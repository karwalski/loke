Tests `core.models.queue` by importing it (X7.2), with `core.models.queuetypes` for `$jobqueue`, `$queuejob`, `$jobpriority` and `$jobstatus`. The file it replaces declared its own queue and its own transitions, and so passed throughout against four functions the module's own comment describes as having been **infinite loops** — `let lv=1` as a break and `let i=i+1` as an increment both declared new bindings, so the loop neither advanced nor terminated, and `queue.jobs.set(i;njob)` discarded its result into a `void` return. Covers `newqueue` (including `maxconcurrent:1`, the limit that protects a single local model), the **priority ordering** `nextpending` depends on (a user request must outrank an agent's, which must outrank a background evaluation — reordering these would put an overnight job ahead of the person waiting), every `statuslabel` and `prioritylabel` variant, `jobispending`, and `nextpending` selecting by priority rather than insertion order and skipping non-pending jobs. Queues are built with `$jobqueue` literals throughout, which is forced by **finding 1**. Four findings, all reported and not fixed: **(1)** `enqueue` does not enqueue — it generates an id, logs "queue: enqueued job", and returns the id; the job is never added, and since the signature returns `str` there is no updated queue for a caller to receive, so correct behaviour is not expressible through it. Nothing outside the module calls it, so it is inert rather than actively wrong. **(2)** `nextpending`'s empty case cannot be asserted: it returns a result whose error arm T-18 makes dead, so the `$ok` arm binds the `$lokeerr` payload and reading `.id` segfaults; it needs a plain form with a sentinel, as `core.providers.types.nocompletion` and `core.optimiser.cache.nohit` both have. **(3)** After any transition, reading the job's **status segfaults** — all four transitions pass a bare variant name (`withstatus(job;$running;…)`) where a constructed `$jobstatus{$running:0}` is required, toke accepted it with no diagnostic, and matching the field later faults; localised by bisection (`.id` and `.startedat` read correctly, `statuslabel(j.status)` faults) and re-verified on a freshly rebuilt archive. So the transitions do run and do write their timestamps, but the one field they exist to change cannot be read back — anything listing the queue for a user crashes. The status reads are therefore not made; the test proves the transition ran via the string fields instead. **(4) RED, two assertions**: all four transitions return `$jobqueue{jobs:jobs}` and omit `maxconcurrent`, so the concurrency limit is reset on every state change. Depends on `std.test`, `std.str`, `core.models.queuetypes`, `core.models.queue`.
