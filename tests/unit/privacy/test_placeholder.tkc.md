The import was present but commented out — `(* i=ph:core.privacy.placeholder; -- linker issue, stubbed below *)` — and the linker gap that note blames closed upstream (`UPSTREAM.md:77`). The copy had drifted: the real `newmap` takes no arguments and no request id, `makeplaceholder` takes a `u32`, and there is no `lookup` or `reverselookup` in the module at all, so three of the fourteen assertions were about functions that have never existed. The consequential one is `addentry`: the stub's returned the updated map — the shape the module should always have had — while for the whole life of LS1.1a the production body was `map.entries==str.arraypush(…)`, a discarded comparison (T-26) around an append to a by-value parameter in a function declared `void`. The map never stored an entry and every restoration returned the model's text with the placeholders still in it, with this test green throughout. Deliberately does not repeat `test_placeholder_collision.tk` (assignplaceholders, longest-first substitution, salt propagation, round trips). Covers instead: the placeholder format in both salted and unsalted shapes; `saltforrequest`'s four-character prefix including the short-id path that would trap under `str.slice`; `newmap`/`addentry` returning a map that holds the entry and not mutating the caller's; `mapfromentities`, including that a map built before placeholders are assigned restores nothing silently, so the ordering dependency is asserted rather than folklore; `restore` on empty and on placeholder-free text; **the prefix asymmetry the module cites as its reason not to sort** — `[EMAIL_1]` must not consume the prefix of `[EMAIL_10]`, which nothing checked and which no round-trip test could catch; and the two ends of `applytotext`'s selection loop, `longestvaluelen` as the seed and `nextinorder` returning -1 on exhaustion.
