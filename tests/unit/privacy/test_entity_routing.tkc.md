Tests `core.privacy.entityrouting` by importing it (X7.2); it previously declared its own route table. Covers the table's shape — including that `count` agrees with `routes.len`, since every loop in the module iterates to `count` and a disagreement would skip routes or read past the end (which segfaults rather than returning nonsense) — the routes that do resolve, and that every declared route names at least a preferred layer. **Records two findings.** (1) THE VOCABULARY MATCHES NO DETECTOR: the five routes are spelled `email`, `phone`, `person`, `creditcard`, `address`, while `core.privacy.regex` emits `phone_au`, `credit_card`, `au_tfn`, `ssn_us`, `ip_v4`, `url`, `api_key` and Presidio emits `PHONE_NUMBER`, `CREDIT_CARD`, `PERSON`, `EMAIL_ADDRESS` — so only `email` matches anything any layer produces, and `hasroute("credit_card")` is false while `hasroute("creditcard")` is true (X7.6's naming split). (2) An unrouted type resolves to a route with **both** layer lists EMPTY rather than to a default or an error, so a caller reading it as "which layers scan this entity" concludes *none* — fail-open, silently, for four of the five types the table was written to cover. Neither is fixed: the module has no importer anywhere, and `core.privacy.pipeline` runs every enabled layer over the whole text rather than consulting a per-entity table. Following the precedent in `tests/unit/storage/test_backup.tk` the assertions record the behaviour as it is; the naming ones turn RED when the vocabularies are reconciled. Depends on `std.test`, `std.str`, `core.privacy.entityrouting`.
