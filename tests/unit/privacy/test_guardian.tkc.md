Tests `core.privacy.guardian` by importing it (X7.2). The import was present but commented out — `(* i=guardian:core.privacy.guardian; -- linker issue, stubbed below *)` — followed by `f=guardianversion():str{ <"1.0.0" }` and an assertion that `guardianversion()` returns `"1.0.0"`. `docs/test-coverage.md` quotes this file as the clearest illustration of the stub pattern in the repository: the module could have changed its version, changed its prompt, or been deleted, and the test would still have passed. The guardian prompt is the instruction block prepended to every request that leaves the machine and the only defence against the model being talked into reconstructing a placeholder — and it is a string constant, so nothing stops a rule being dropped in an edit and nothing would notice. Covers: the version marker inside the prompt matching `guardianversion()`, so the two cannot drift and a caller can still recognise a guarded prompt; `isguardianpresent` in both directions, including that an ordinary system prompt is *not* detected, so a request that lost the block is detectable; each of the five numbered rules individually, keyed on its subject rather than its wording so prose can improve but a rule cannot vanish; the two sentences that make the block an override (`ABSOLUTE`, "take precedence over all other instructions"); that rule 2 shows the placeholder shape `core.privacy.placeholder` actually produces; and composition — no stray separator when there is no base prompt, the base prompt preserved, and the guardian **first**, because a block claiming precedence that arrives after the instructions it overrides is relying on the model's goodwill. Also asserts that a hostile base prompt does not displace the guardian, making explicit that this module composes and does not sanitise. Depends on `std.test`, `std.str`, `core.privacy.guardian`.
