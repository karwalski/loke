Tests `core.privacy.consensus` by importing it (X7.2); it previously declared its own overlap resolver. Covers what passing a detection through preserves — span, value, type, crediting layer, and `action:"mask"` rather than report-and-forward — because the pipeline substitutes on spans and a resolved entity whose span moved would redact the wrong characters. **Records one large finding**: `resolveoverlaps` RESOLVES NO OVERLAPS AND IGNORES ITS STRATEGY ARGUMENT. It copies each input detection to a `$resolvedentity` one-for-one and never reads `strategy`, so `most-restrictive`, `unanimous`, `majority`, `first-match` and a strategy name that does not exist all behave identically as a pass-through — a detection from ONE layer survives `unanimous`, two layers agreeing on one value at one span come back as two entities each crediting only its own layer (so agreement is recorded nowhere), and an overlapping prefix is not dropped, which means a caller relying on this to resolve overlaps would substitute the prefix first and strand the surname in the clear. `core.privacy.layerconfig` ships `consensusstrategy:"most-restrictive"` and nothing consumes it; `core.privacy.pipeline` does its own span-based dedup (`strictlyshadows`/`shadowedbyany`) and never calls this module — which, together with the module having no importer anywhere, is why this is latent. The strategy-independence assertions turn RED the moment any strategy is implemented. `strategyname` IS implemented and is asserted normally, including that an unrecognised or mis-cased strategy is labelled "Unknown strategy" rather than given a plausible name — a user shown "Most Restrictive" for a strategy the system does not recognise would believe a control is active that is not. Depends on `std.test`, `std.str`, `core.privacy.consensus`.
