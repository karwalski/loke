A budget manager built inside a request handler and thrown away at the end of it is not a budget — every request starts from zero and the limit never binds — so the handler persists its counters through the settings store and, because `setint` returns `i64!$lokeerr` and T-18 makes its own report of success unreadable, verifies the write by READING IT BACK. That read-back is the entire guarantee. Covers: `daynumber` being a plausible day count that does not move within a request (the key the counters reset on); `persistbudget` succeeding and the figure surviving into a freshly built manager, so the limit binds across requests; a second write replacing the first rather than being ignored; `persistbudget(0;…)` reporting FAILURE rather than claiming to have recorded, and `budgetmanager(0)` starting from real default limits with nothing used — an unpersisted budget is restrictive, not unlimited; `formatusage` reporting the persisted figure; the three refusal bodies (`refusedroute`, `refusedbudget`, `refused`) each returning a response handle, and being distinguishable because a routing refusal is a configuration problem and a budget refusal a spending one; and `completionfor` carrying the routed model, exactly one user message whose content is the ANONYMISED text verbatim and contains no address, the guardian system prompt, and `stream:false` — the interactive endpoint must not ask for a stream it cannot restore placeholders in. Note: the counters are read with `core.optimiser.budget.rowtokens`, not `m.usage.tokensused` — `usage` is an ARRAY of per-period counters, so the direct spelling reads an array header as a struct and yields a pointer value (measured at 4387275664 where 1234 was expected).
