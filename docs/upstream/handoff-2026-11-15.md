## 3. New issues

### T-67 — an integer is accepted where the runtime reads a pointer, and the process dies

**Severity: silent until it crashes. It is the half of T-60's spawn ask that 138.21 did not cover.**

**Measured** at 3.1.0 and 3.2.0 ([`repro-2026-11-15/T-67/`](repro-2026-11-15/T-67/)):

- `process.wait(5)` checks clean, builds, and the program dies with SIGSEGV (exit 139).
  `process.wait(4096)` and `process.stdout(7)` do the same. (`repro.tk`)
- `process.wait(0)`, the NULL handle a `$err:e 0` arm yields, answers -1. loke's idiom is
  safe, and 138.21 kept it legal on purpose. (`zero.tk`)
- **The shape loke writes.** `handle` cannot be named in a parameter (`h:handle` is E2005,
  138.32), so a loke helper that takes a process handle declares `h:i64`
  (`packages/core/src/installer/detect.tk`, `ollamacli.tk`, `install.tk`). A real handle passes
  through it correctly, and so does any other integer: `waitfor(5)` checks clean and segfaults.
  (`laundered.tk`)
- **The same class in `std.str`.** 56 of `str.tki`'s 105 members are still `gen:"abi"`, 41 of
  them with every parameter declared `i64` (the same 56 as at 3.1.0; T-36's residue). 3.2.0's new
  check refuses an array where the runtime reads a C string (`str.toupper(@("x"))` is E4031,
  "read by the runtime as a C string"), but not an integer: `str.toupper(42)` and
  `str.reverse(12345)` check clean and segfault. (`abistr.tk`)

**EXPECTED:** each refused at `--check`, or answered as the NULL handle is (-1, `$err`) rather
than dereferenced.

**Workaround in loke:** none needed today. loke passes only real handles and the `0` filler, and
only strings to `std.str`. The point is that 138.21's check, which loke welcomed, never reaches
loke's own handle passing, because every helper parameter that holds a handle is an `i64`.

**Ask, either of:** (1) let a program name `handle` (and the other opaque std records) as a
parameter type, so the checker judges a helper's call sites as it now judges std's own slots; that
is 138.32's option (b). (2) Have the process runtime refuse a handle it did not create (a registry
of live handles, or a tagged header), answering -1 / `$err` as for NULL. (2) also covers a forged
value that reaches the runtime by another route. For `std.str`, type the remaining `gen:"abi"`
members (T-36's original ask), or extend the C-string check to an integer argument.

### T-66 — a `mt` with variant arms on an i64 passes `--check`

**Severity: a check-only target never sees it. At build the error is located, so not silent.**

**Measured** at 3.1.0 and 3.2.0 ([`repro-2026-11-15/T-66/`](repro-2026-11-15/T-66/), T-2's
program): a three-arm `mt` labelled with `FileErr` variants on a parameter declared `i64` is
`--check` rc 0, and the build stops with `error[E9005]: match has 3 arms, but the sum type of
the matched value is not established`, at the `mt`.

3.2.0 closed this class for an unrecognised label (E3011, 127.292) and for a record subject
(E4080, 127.367), each of which "failed at build" before. An i64 subject is the case left.

**Ask:** refuse variant arms on a subject that is not a sum or a result at `--check`, as E4080
does for a record. Low priority: loke has no such match in its linked trees.

### T-65 — a parameter named `t<digits>` collides with toke's IR temporaries

**Severity: build break after a clean `--check`. loke has no such parameter.**

**Measured** at 3.1.0 and 3.2.0 ([`repro-2026-11-15/T-65/`](repro-2026-11-15/T-65/)):

```toke
f=g(t0:i64):i64{
  <t0+1
};
```

`--check` rc 0; clang: `multiple definition of local value named 't0'` (E9003, "while compiling
f=g"). The parameter's slot is `%t0` and so is the first temporary. A parameter `t5` collides
with the fifth temporary the same way. A local `let t0=4;` is fine.

**Ask:** name parameter slots so they cannot collide (the incoming value is already `%t0.arg`),
or refuse the name at `--check`. Found writing a reproducer; it cost one rename.

### T-39 (reopened) — `unused-import` is still unsound for two shapes, and `--check` misses one

**Severity: `--lint --fix` produces code that does not compile. Found by loke's LS1.3 sweep
(W123), which removed none of its 9 remaining `unused-import` diagnostics because every one
failed to compile once removed.** Our 2026-11-15 status ledger first recorded T-39 as fixed from
the param-type case alone; that was wrong, and is corrected.

**Measured** at 3.2.0 ([`repro-2026-11-15/T-39/`](repro-2026-11-15/T-39/), `TOKE=... sh run.sh`
in each directory):

1. **An import used only as a struct-field type** (`typeonly/`). `defs` declares `$item`;
   `fieldonly.tk` imports it only for `t=$holder{items:@$item;k:i64}`. `--lint` reports
   `unused-import` (so does a scalar field `it:$item`; a parameter type `x:$item` is correctly
   not flagged). After `--lint --fix` the import is gone and `--check` fails E3011
   "identifier 'item' is not declared".
2. **An import needed only to resolve a field of a struct another module returns**
   (`fieldres/`). `user.tk` calls `srv.handle(x)`, which returns `proto`'s `$res`, and reads
   `r.text`; it imports `proto` for nothing else. `--lint` reports `p` unused. After
   `--lint --fix`, **`--check` passes**, and compiling fails E4034 "no struct in scope
   declares a field 'text'". So there are two defects here: the false positive, and a
   `--check` that accepts what the compile refuses.

**Ask:** count a struct-field type and a field resolution as uses; and make `--check` resolve
fields the way the compile does (or have the compile resolve the returned type's fields
without the import, which would make the import genuinely unused). loke keeps all 9 imports.

## 4. Still open from the earlier handoffs

### 138.20 (T-60) — `==` on arrays

**Measured at 3.2.0** (W117, [`repro-2026-11-09/results-v3.2.0-ea7ddf22.txt`](repro-2026-11-09/results-v3.2.0-ea7ddf22.txt)):
unchanged. `let a:@str=@(); a==@()` is false with `a.len` 0 (an address compare against a fresh
block); `@(1;2)==@(1;2;3)` and `@(256)==@(512)` are true (`tk_str_cmp` over the array blocks).

**What loke needs:** either outcome your register lists (item 1.2). A refusal pointing at `.len`
would turn loke's gate script (`scripts/find_empty_array_sentinel.py`, which fails any `== @()`)
into the compiler's job, and loke has no array `==` that wants element-wise meaning. The silent
answer is the only thing loke cannot use.

**Priority to loke: 2.** Silent, and it hid every failed spawn in loke once; the gate holds it.

### 138.24 and 138.25 (T-63) — a client that can fetch an untrusted URL safely

**Measured at 3.2.0** (W117): a server sending one body byte every 5 s holds `http.geturl` for
40,383 ms and the call answers `$ok`; a 64 MiB body is read whole and answers `$ok`. The
rebinding gap (the client resolves inside connect and takes no address; std has no general
resolver) is read from `src/stdlib/http.c`, not measured.

**What loke needs, against your register's recommendations (items 2.1 and 2.2):**

- **138.24, opt-in controls, defaults off** (2.1 (a)) is what loke asked for: controls, not
  defaults. The deadline should cover connect, TLS handshake, headers and body together, and the
  body cap should stop the read, not truncate a body that is then answered `$ok` (an over-cap
  body as `$err`, as 138.23 now does for a short one). Your 138.34 (the documented
  `timeoutms` is per read) fits in the same amendment.
- **138.25, a `connectaddr` option plus `net.resolve(name):[str]!neterr` gated by `net`** (2.2)
  covers loke's use: moke resolves, checks every address against its private/loopback/metadata
  rules, and connects to the address it checked while the certificate is verified against the
  URL's name. A resolver gated by `net` costs loke nothing (moke holds `net`).

With both, moke's `/api/proxy` drops the system curl (`moke.proxy.fetch`, `--resolve`,
`--max-filesize`, `--max-time`) and keeps `packages/moke/tests/test_proxy_fetch.tk` as the
acceptance test, as your row for 138.25 already notes.

**Priority to loke: 3.** loke's workaround is complete; the cost is a subprocess per fetch.

### 138.27 (T-58 addendum) — a GET that carries headers

**Read at 3.2.0, not measured:** `http.tki` has no such call (`geturl(str)` and
`clientget(httpclient;str)` take no headers).

**What loke needs:** the call as your register proposes (item 2.3),
`http.getheaders(url:str;headers:[[str]]):httpresp!httperr`, with 138.8's rules. loke's update
checks (`core.update.checker`, `cli.updater`) call GitHub's API, which requires a `User-Agent`;
they answer "no update" without sending until then (loke VM1.6g, F10.41).

**Priority to loke: 4.**

### 138.19 (T-59 / B9) — scoped capability grants

**Measured at 3.2.0** ([`repro-2026-11-15/T-59/`](repro-2026-11-15/T-59/), loke's own probe):
points 1, 4, 5 and 6 of T-59 are unchanged. A binary built with `fs_read = "/nonexistent-dir-only"`
reads `/etc/hosts`; one built with `net = "10.255.255.1:9"` is granted `net`; loke's manifest
(no `env_write`) runs `env.set` when started with `--allow-env`; `env = true` grants env_write
with no warning; `enforce = false` still traps CAP001 (the safe behaviour; the documentation is
what is wrong). Points 2 and 3 are read from source.

**Thank you for the story number** (138.19, our question last time) and for the design note.
From your register's summary of it (item 3.4; the note itself is on `feature/z136-design-notes`,
which loke has not read): runtime flags that narrow a baked set would answer loke's launcher
point, direction-prefixed `net` scopes its listen/connect point, and a warning release before a
quoted string changes meaning costs loke nothing, since loke grants every class as bare `true`
for exactly this reason. loke has no view to add on D1–D5 beyond its original ask.

**What loke does meanwhile:** grants `fs_read`, `fs_write`, `net` and `process_spawn` as bare
`true` with the intended scope in a comment, measures the grants in its gate
(`scripts/check_capabilities.sh`), and keeps traffic on the machine with its own transport rule
and `scripts/check_loopback_binds.py`, not the manifest.

**Priority to loke: 5.** Question: is there a date for D1–D5?

### 127.319 — std `T!E` results forced to be matched

**Measured at 3.2.0** ([`repro-2026-11-15/127.319/`](repro-2026-11-15/127.319/)):

### 138.32 — may `handle` be named in type position?

Your register recommends leaving it unnameable (item 1.12, option (a)), on the ground that after
138.21 "the checker judges the value, so no annotation is needed for safety". **T-67 is loke's
evidence that the annotation is needed** for a program that passes a handle to its own
function: the value is judged in std's slots, not in a user parameter that has to be spelled
`i64`. loke would take either (1) or (2) of T-67's ask; if (2), the runtime check, 138.32 can
stay as recommended.

## 9. Reproducing

```sh
cd docs/upstream/repro-2026-11-15
TOKE_DIR=/path/to/toke ./run.sh                    # everything (about 2 minutes)
TOKE_DIR=/path/to/toke ./run.sh T-67 T-65 T-66     # a subset; RW = the 2026-09-27 rewrites
```

- `TOKE_DIR` is a toke checkout with the built `toke` binary. No ooke is needed.
- Each line is `ID | verdict | observed`: DEFECT (as filed), OK (expected), OPEN (an open ask
  whose motivating behaviour was observed: T-59, 127.319, 138.32), or note. Build products go to
  `$TMPDIR/loke-repro-2026-11-15/<toke commit>`.
- Servers bind `127.0.0.1` ports 47990–47999 only and are stopped by PID; nothing leaves the
  machine. T-64 takes about 65 s (two 30 s read timeouts). T-67's probes crash on purpose
