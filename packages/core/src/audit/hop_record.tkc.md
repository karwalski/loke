The per-hop record of a `loke ask` dispatch (F5.3), written with the modules the browser request path (`page.api.pipeline`) writes its own with, so there is one disclosure mechanism. `factsof(run;usecase;fbreason;fbby)` takes, once, what every row carries from the privacy run: the request id, sensitivity and risk tier as labels, entity types and counts (`entitysummary`, never a value), the detection layers that scanned and were skipped (`detectionlayers`), and the redact-and-forward selection (NC1.8; `loke ask` passes `user_choice` by `user`). `hopid(facts;i)` is hop i's correlation id: the request id, then `<id>-h<n>`, as F5.3a set for the browser. `recordlayers` writes the run's per-layer metrics on the request id before any audit row (F3b.10). `reserve` is the disclosure reservation and its `llm_dispatch` audit row in one transaction (`core.audit.disclosure.reserveaudited`, DA1.7/DA1.9), from the exact body's octet count; false means the hop must not be sent. `outcome` completes the row with its `llm_request` or `llm_request_failed` audit row in one transaction (`completeaudited`), then writes the decision trace (`core.governance.trace`, policy `not_evaluated`, since the CLI evaluates no organisation policy) and the metrics_raw row. `refused` audits a hop that sent nothing (`kill_switch_refused` or `llm_request_refused`) with its trace and no disclosure row; `privacyrefused` audits a run the filter refused. Every function takes the store and does nothing on 0. Called by `core.router.fallback.dispatchchain` and `cli.ask`; the browser request path (`page.api.pipeline`) writes its entity summary, detection layers and risk label with `entitysummary`, `detectionlayers` and `risklabel` here, so both paths record the same facts for the same input (F5.3, `tests/integration/test_hop_facts_parity.tk`). Tested by `tests/integration/test_ask_disclosure.tk` and, over the built binary, `scripts/smoke_privacy_harness.sh`.
