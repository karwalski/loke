The single entry point for loading a built-in policy preset by name, and the bridge from `$policy` to the `$regulation` and `$policyset` shapes `core.policy.loader.evaluate` consumes. Exports `names`, `hasname`, `byname`, `isknown`, `isknownname`, `rulesfor`, `approvalthresholdfor`, `crossborderallowedfor`, `jurisdictionfor`, `regulationfor`, `policysetfor`, `policysetformany`, `defaultset` and `allregulations`. Depends on `core.policy.schema`, `core.policy.types`, the seven preset modules, `std.str` and `std.time`.

This module exists because there were two parallel systems. `core.policy.regulations` held a hand-written `$regulation` per regulation and `core.policy.presets` held a richer `$policy` per preset; neither had a single importer, and the duplication had already produced a substantive defect — `regulations.ukgdpr()` was a verbatim copy of `gdpr()`, `gdpr-` rule ids and the text "must not leave EU without adequacy decision" included, under `jurisdiction: "UK"`. `core.policy.presets` is now the source of truth, `core.policy.regulations` is deleted, and `$regulation`/`$policyset` are a derived view rather than a second definition. Each preset module owns both its configuration (`preset()`) and its evaluable rule list (`rules()`), so the two cannot drift apart again.

Not-found is a sentinel struct plus a predicate (`unknown()` and `isknown()`), not a `$policy!$err`: under T-18 a match on a user-declared error side always takes the first arm, so an `$err:` arm would be dead code and every unrecognised name would be reported as a successfully loaded policy. `approvalthresholdfor` and `crossborderallowedfor` exist so a consumer can read those two settings without importing `core.policy.schema` into its own scope — doing that in `core.governance.rulesengine` would place `$anonymisationrule.action` at offset 1 alongside `$compoundrule.action` at offset 4, which is the E4034 shape that breaks an unrelated module.
